# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope — where work goes

Read this before editing. The details are in **Architecture** below; this is the rule.

| Path | Status |
|---|---|
| `crates/desktop` | The frontend. Work here. |
| `crates/web/static` | The shared JavaScript client — the desktop app ships it. Work here. |
| `crates/core`, `model`, `lsp`, `logic`, `grid` | The shared core. Work here. |
| `crates/tui`, `crates/coon`, `crates/web/src` | **Deprecated. Do not do new work in these.** |

Deprecated means kept working, not frozen out. In those three paths:

- **Do** fix them when a change to `core` or `protocol` breaks their build, and
  fix a test they catch. A break there is a change to fix, not a reason to
  delete the crate. They are still workspace members and still tested.
- **Do not** port a desktop feature across, refactor, clean up, or improve them
  in passing. A feature belongs in the desktop app and the shared client and is
  not expected to reach the other two.

If a task asks for work in a deprecated path, check whether it actually wants
the desktop app, and say so rather than building it twice. Each of those
directories carries its own `CLAUDE.md` repeating this where you will land.

## Commands

```bash
# Build
cargo build
cargo build --release

# Run — `cargo run` is the desktop app; `-p desktop` is the same thing spelled out
cargo run                              # Desktop app, demo mode (no clangd needed)
cargo run -- /path/to/project          # Desktop app, LSP mode (real C/C++ project via clangd)
cargo run -- /path/to/project --flavour src/foo.c   # …analysing only the build that file is compiled as

# Load a project headlessly and print what came out — the acceptance harness
cargo run -p core --example load -- /path/to/project [--flavour src/foo.c]

# Deprecated frontends — `coon` is outside default-members, so name it
cargo run -p coon                              # TUI, demo mode
cargo run -p coon -- /path/to/project          # TUI, LSP mode
cargo run -p coon -- --web 8080                # Web frontend, demo mode
cargo run -p coon -- /path/to/project --web 8080   # Web frontend, LSP mode

# Test
cargo test                       # All tests
cargo test -p lsp                # LSP crate only (requires clangd in PATH)
cargo test -p logic              # Graph logic only
cargo test <test_name>           # Single test by name pattern
```

LSP integration tests require `clangd` to be installed and in `PATH`. See `lsp/TESTING.md` for details on writing integration tests.

`LspClient::new` runs `clangd` from `PATH`; set `COON_CLANGD` to the full path of a
particular binary to use that one instead. If `COON_CLANGD` is set but names nothing
executable, startup fails rather than falling back to `PATH` — picking a different
clangd than the one asked for is how an index ends up quietly wrong. Either way the
choice, and where it came from, is logged at info on startup.

Logs are written to `logs/` directory.

## Architecture

COON is a Rust workspace that visualizes C/C++ call graphs, using `clangd` as the analysis backend. It ships **three frontends** over one shared application core — the desktop app, and the TUI and web server it replaced.

### Crates

- **`model`** — Shared types: `CallGraph`, `FunctionNode`, `CallEdge`, `SymbolId`, LSP progress/status enums.
- **`lsp`** — All clangd communication: `LspClient` (raw protocol), `LspService` (higher-level async service with request/response handling, document caching, symbol resolution).
- **`logic`** — Pure graph algorithms (BFS traversal, path-finding, reachability) operating on `CallGraph`.
- **`core`** — Frontend-agnostic application core. `CoreApp` (owns `CallGraph`, `LspBridge`, `CoreWorkspaceManager`) exposes `dispatch(Command) -> Vec<AppEvent>` and `tick() -> Vec<AppEvent>`. Also holds `layout::compute_layout` (node positions), `protocol` (the shared wire format), `boot::spawn_lsp_bridge`, `demo`, and `logging`.
- **`grid`** — Tree/DAG layout algorithm (a workspace crate, used by `core::layout` and the TUI).
- **`desktop`** — The `coon-desktop` binary: Tauri v2 shell hosting the client in `crates/web/static`. **The frontend**, and the binary a bare `cargo run` launches.
- **`coon`** — *Deprecated.* The `coon` binary: CLI parsing, and the TUI + web runners.
- **`tui`** — *Deprecated.* Ratatui TUI: `TuiApp` (main state/event loop), `GraphView`/`GraphViewState`, search bar, workspace management.
- **`web`** — *Deprecated server, live client.* Axum server: WebSocket at `/ws`, client assets embedded via `rust-embed`. The Rust is what is deprecated; `static/` is the shared client and the desktop app's `frontendDist`.

### Frontends

| Frontend | Entry point | Transport to `CoreApp` | Status |
|---|---|---|---|
| Desktop | `coon-desktop` (default) | JSON over Tauri IPC | Where frontend work goes |
| Web | `coon --web <PORT>` | The same JSON over a WebSocket | Deprecated |
| TUI | `coon` | Direct calls — no serialisation | Deprecated |

**The desktop app is the default; the TUI and the web server are deprecated.** Deprecated means kept working, not frozen out: both still build, still run, are still covered by the workspace's tests, and both still have to compile after a change to `core` or `protocol` — a change that breaks them is a change to fix, not a reason to delete them. What stops is new work: a feature belongs in the desktop app and the shared client, and is not expected to reach the other two. Neither is `#[deprecated]` as an attribute, because `coon` is their only caller and is deprecated itself, so the warnings would land nowhere that does not already say so. The notice a user sees is `main::warn_deprecated`, printed to stderr before the TUI takes the terminal.

Two consequences in the manifests, both deliberate: `crates/desktop` is in `default-members` and `crates/coon` is not — `cargo run` picks a binary from the default set and refuses if there are two — which is also why a bare `cargo build`/`cargo test` now compiles the Tauri tree it used to skip. And `crates/web/static` is not deprecated with the crate around it: it is the client the desktop app ships, so client work goes there exactly as before.

The web and desktop frontends **share one JavaScript client** (`crates/web/static`). They differ only in `transport.js`, which feature-detects `window.__TAURI__` and picks either a WebSocket or Tauri `invoke`/`listen`. Because both backends emit identical `core::protocol::ServerMsg` shapes, `app.js` needs no knowledge of which one it is talking to. Keep it that way: put shared behaviour in `app.js`, and anything pipe-specific (including window management, via `CoonHost`) in `transport.js`.

Client assets are vendored, not CDN-loaded (`static/vendor/cytoscape.min.js`), because the desktop app must work offline.

### Client files

| File | Holds |
|---|---|
| `theme.css` | Design tokens only — colours, type scale, 4px spacing grid, shell metrics. Light and dark. |
| `app.css` | Component styles. Reads tokens; defines no raw colours. |
| `transport.js` | The pipe (WebSocket vs Tauri IPC) and `CoonHost` window controls. The only file that touches `__TAURI__`. |
| `palette.js` | The command palette / fuzzy picker. Generic: callers hand it items and get a pick callback. Knows nothing about commands or symbols. |
| `app.js` | Everything else: tabs, graph, sidebar, breadcrumb, status bar, commands, keybindings. |

`Ctrl+Shift+P` opens the command palette, `Ctrl+P` the symbol finder. **New user-facing actions belong in `buildCommands()` in `app.js`, not as another toolbar button** — that's how the commands `core` exposes stay reachable without the chrome growing a control each time. The toolbar's four controls are the exception that defines the rule: depth, direction, orientation, and the map's grouping are *settings whose current value has to be visible*, not actions. A palette entry can invoke a setting but cannot show you what it is, and each of these is something a reader of the canvas needs to know to read it. Everything else goes in the palette, and each of these is in the palette too.

The fourth of them is a pill that opens a panel (`#cluster-menu`), and it is where a *set* of related settings goes. It reads out the two values the canvas needs — the method and how many boxes are on screen — and holds the rest behind a click: the method with its description, the one knob that method reads, how far the ladder coarsens, and which rung is drawn. It replaced a zoom stepper beside a method dropdown, which put the same setting in the toolbar twice as soon as the knobs arrived. The rule it follows: the pill is the readout, the panel is the tuning, and nothing in the panel is drawn from anything written in the client — the ranges, steps, labels and defaults all come off the snapshot (`cluster_methods[].grain`, `cluster_top`), so a knob retuned in `logic` is retuned here too.

**Every view setting is remembered, in one `localStorage` object under `coon.prefs`.** The backend persists nothing — not the depth, not the direction, not which algorithm built the map — and there is no config file, so what survives a restart survives it here: depth, call direction, orientation, the cluster settings and grouping, the theme, and the sidebar's width and collapsed state. One object rather than a key per setting, because they are read together on every snapshot and a store you can print is one you can reason about when a setting comes back wrong. (`coon.theme` is the key the theme moved out of, still read once so nobody loses a pinned one.)

`restoreWorkspace` hands the view settings to a workspace **the first time this client sees it**, which makes one mechanism do two jobs: the restore after a restart, and the default a new tab opens with. First sight only, and never again — a preference that kept re-asserting itself would undo every change made after it, which is the one way a remembered setting is worse than no memory. It restores with *absolute* commands, which is why `Command::SetCallDirection` exists beside `ToggleCallDirection`: a restore knows which way it wants to read, and "the other one from whatever is there" is a coin flip dressed up as a setting. The sidebar is chrome rather than a view setting, so it is applied at load instead of handed to a workspace — waiting for a snapshot to size it would show it at one width and then another. What is stored for the grouping is the *box count*, not the rung number, for the same reason every control reads that out — a ladder built to other settings is a different height, so rung 3 of one is not rung 3 of the next, where "about twenty boxes" means the same on both, and the restore lands on the rung closest to it.

### Readability at scale

A whole call graph is unreadable by default: rooting at `main` in the demo reaches 56 nodes. Four mechanisms keep it legible, and they are the first things to reach for before adding more visual weight:

| Mechanism | Where |
|---|---|
| **Depth limit** (`Command::SetGraphDepth`, per workspace, default 3, or none at all) | `core::layout` stops the BFS |
| **Collapse** (`Command::ToggleCollapsed`, per workspace) | `core::layout` stops descending; client drops the node's outgoing edges |
| **Expand** (`Command::ExpandFunction`, per workspace) | `core::layout` walks one level *past* the limit at those nodes |
| **Hover focus** — fade everything non-adjacent | `app.js`, transient |
| **Map zoom** (`Command::SetMapLevel`, per workspace) — the map's own control, since it has no depth to limit | `logic::cluster` builds the rungs; `core::layout` draws one |

**The depth limit can be taken off.** `layout::GraphDepth` is `Levels(n)` or `Unlimited`, and the second is the *absent* bound rather than a large number: there is no number that means "as far as the calls go", and a `usize::MAX` sentinel is something every reader between the stepper and the BFS has to be told about. `Unlimited` travels as `null` — so `{"SetGraphDepth":4}` still means what it always did — and is not clamped to `MIN_DEPTH..=MAX_DEPTH`, because the range is what keeps a *number* meaningful. It terminates on a cyclic graph for the same reason the bounded walk does: the BFS enqueues a symbol the first time it sees it and never again. `expanded` decides nothing when there is no limit to walk past, and `collapsed` decides as much as it ever did. It is the one mechanism in this table the user can switch off, so it is a thing asked for and never a default: rooting near the top of a real project reaches thousands of nodes, which is what the limit exists to prevent. In the client it is a **separate toggle inside the depth pill**, past a divider, and not a ninth position on the stepper: which number, and whether a number applies at all, are two questions, and a `+` that walks off the end of its own range answers the second one by pretending it is the first. The stepper is `DEPTH_MIN..=DEPTH_MAX` and nothing else; the `∞` beside it lights at full accent the way the orientation control's live segment does, and while it is lit the `−`/`+` are dimmed rather than hidden — the range is still what the toggle comes back to, and a control that vanishes makes the toolbar jump. What it comes back to is `lastBoundedDepth`, the number that was showing, stored beside the depth as `depthLevels`: turning the limit off must not quietly change the limit, and landing on the default afterwards is exactly that. Both directions are in the palette too, named absolutely — a palette is searched for what you want, not read for what you have.

Nodes hiding children are dashed and labelled `+N`. Auto-fit is clamped at both ends (`MAX_FIT_ZOOM` / `MIN_FIT_ZOOM`): a small graph must not render at cartoon size, and a large one must not shrink past readable — below the floor it holds the zoom and anchors on the focused node so the user pans.

Design rules worth keeping:

- **Sans for chrome, mono for code.** Function names and namespaces get `--font-mono`; every label, tab and button gets `--font-ui`. Reaching for monospace everywhere is what made this read as a terminal.
- **One accent.** State is carried by accent strength and a left/top accent bar, not by a different hue per state.
- **Nodes sit on a fixed grid.** `core::compute_layout` lays out in the same pixels the canvas draws in and returns node **centres**, so the client uses positions verbatim. Graph nodes use a fixed `NODE_W` with truncated labels; label-sized nodes overlap their neighbours as soon as a C++ symbol name gets long. Keep `NODE_W`/`NODE_H` in `app.js` in step with `NODE_WIDTH`/`NODE_HEIGHT` in `crates/core/src/layout.rs`.
- **Orientation is a transpose, not a `grid` setting.** `grid::TreeOrientation` exists but the Sugiyama pass ignores it: levels always advance along x. `core::layout` gets top-down by swapping the node size going in and the coordinates coming out, so both orientations share one code path. The *spacing* is not transposed with it: a node is 150×32, so top-down advances levels along the short axis and spreads siblings along the long one, and reusing the left-to-right gutters gives a flat stripe. Top-down has its own pair (`*_TOPDOWN`) — generous between levels, tighter between siblings. Per workspace, via `Command::SetGraphOrientation`. The toolbar shows it as a segmented control — both options visible, the live one lit — because a single pill whose label is the current state reads as a command that does the opposite of what it says.
- **Levels stretch to fill the canvas.** `grid` packs each axis as tightly as its separations allow, which leaves a wide sibling fan as a band with the levels almost touching and half the screen empty. `layout::balance_aspect` scales the level axis — uniformly, so it is just a bigger pitch and nothing can collide — until the bounding box reaches `TARGET_ASPECT`, capped at `MAX_LEVEL_STRETCH` because past a point spreading levels only means panning further to follow one edge. It runs on the cluster map too, and until the map had a cross pitch of its own it never once fired there: every map came out at the floor, which is a stripe the other way round from the one this checks for. It now fires in the one case `place_boxes` cannot help — few columns and a tall busiest column, which is a scoped map, or any map read top-down, where a column of six 150px-wide boxes spans more than the columns do. The cross axis there is what it has to be, the count floor times the pitch, and the level pitch is the only lever left, exactly as in the tree.
- **`grid` spacing is pitch, not gutter.** `level_separation` and `node_separation` are full centre-to-centre distances, not gaps added to the node's size. `core::layout` derives them as `size + gutter` explicitly, because the crate's terminal defaults (`node_width: 20`, `level_separation: 4`) make the distinction easy to miss — and getting it wrong overlaps every node.
- **A click points; it does not act.** Tapping a node sends `Command::FocusFunction`, which moves `selected_function` and emits nothing at all — the client lights the border and moves the breadcrumb itself, with no rebuild. Every event routes to a snapshot and every snapshot tears the canvas down and rebuilds it, which is far too much for saying "this one". Loading a node's calls is the hover `+` button, and hiding them is a double-click. A node's border carries exactly two states, selected and not: `--accent` at 2px against `--node-border` at 1px, with no fill either way — the ground stays the common surface. Exactly one node is selected at a time. The root wears nothing of its own; it used to take a ring at a lighter weight, which made the border a three-way signal to be measured rather than read, and the breadcrumb says where the tree is rooted anyway. For the same reason the root→selection path is drawn on the edges alone, never by lighting the nodes along it. (Dashed is a separate axis, not a third state: it means a node is hiding children.)
- **Expanding appends; it never re-roots.** Asking for one node's calls adds that node to the workspace's `expanded` set, and the layout BFS — still rooted where it was — walks one level further there. It used to move the BFS origin onto the expanded node instead, which redrew the whole graph around it and dropped every sibling branch. For the same reason the client's auto-fit key is the *root*, not the focused node: appending must not move the viewport the user positioned.
- **This is a DAG, not a tree.** Collapsing a node does not necessarily remove its children from the canvas: another caller may still reach them. Collapse therefore also drops the edges *leaving* the collapsed node, client-side, so the action is always visible.
- Graph styles are read from the CSS custom properties at startup, so the canvas and the chrome stay on one palette.

The desktop window is **undecorated** (`decorations: false`); `#titlebar` is the titlebar and carries the drag region, workspace tabs and window controls. To go back to native decorations, flip that flag in `tauri.conf.json` and the `is-desktop` window controls will hide themselves.

### Data Flow

Every frontend's `main.rs` — `crates/desktop/src/main.rs`, and `crates/coon/src/main.rs` for the deprecated two — has the same two paths, chosen by whether a project path was given:

1. **Demo mode** (`cargo run`): builds a synthetic `CallGraph` and hands it straight to the frontend.
2. **LSP mode** (`cargo run -- <path>`): spins up a background `lsp_loader_task` that connects to clangd, opens exactly one source file from the compilation database, and builds a `CallGraph` via workspace symbol queries. One `didOpen` is all it takes to make clangd read the database and index every file in it, and *which* file is open decides what the query sees — see **Open documents are a cache, not the project** below. The frontend starts immediately while loading proceeds asynchronously. A Tokio MPSC bridge forwards `LspRequest` messages to `LspService` and returns `LspResponse`/`LspUiMessage` results back. `core::boot::spawn_lsp_bridge` performs this wiring for every frontend.

The web and desktop backends both poll `CoreApp::tick()` every 100ms and translate the resulting events through `core::protocol::EventRouter`, which decides what to forward verbatim and when to push a fresh snapshot. The desktop also ticks the moment a clangd reply lands, by awaiting `LspBridge::response_ready` beside its interval: the interval is a ceiling on latency, not the app's pace. The edge warmup ran in lockstep with the poll — eight prepares, wait a tick, eight follow-ups, wait a tick — so 100ms was the whole step: 5.6s on the 221-symbol test project, 0.2s once the tick followed the reply.

### Key Design Patterns

- **Async message passing**: Tokio MPSC channels connect the LSP loader, the LSP service worker, and the TUI — they never share mutable state directly.
- **`CallGraphAdapter`**: Wraps `CallGraph` to abstract call direction (incoming vs. outgoing) so graph traversal and rendering are direction-agnostic.
- **Lazy call hierarchy**: Initial load fetches workspace symbols; per-function call hierarchy is fetched on demand when the user selects a function.
- **A call graph is of one build.** A project's `compile_commands.json` is usually several builds at once, and the same header compiled under two define sets is two different pieces of code: jemalloc's 217 entries are 8 flavours — 68 library files, 112 unit tests with `-DJEMALLOC_UNIT_TEST`, 14 integration tests and five smaller sets — and its tests see `jet_*` declarations where its library sees `je_*`, out of the same headers. With all of them in one database clangd's `outgoingCalls` drops a callee whose symbol the header view currently published lacks, so a call appears or vanishes with whichever TU published that header last: diffing two runs, 194 of 2,444 symbols had different callee sets and 613 of the 626 differing callee locations were `.h` declarations, essentially all `jet_*`. The warmup's three lanes race that, and a click reshuffles it afterwards. So `--flavour <file>` on the desktop app names a source file whose compile command *is* the build: `lsp::compile_commands` keys each entry by its sorted, deduplicated `-D`/`-U`/`-include`/`-imacros` arguments (nothing else — an `-O2` or an include path does not change what the preprocessor reads), the project becomes every entry with that key, and clangd is spawned with a `--compile-commands-dir` pointing at a database of just those. One view per header, and every answer is fixed regardless of what is open. Nothing is guessed when the flag is absent: the behaviour is what it always was — every entry — and the flavours are listed in the log as `count × representative file` plus the defines that distinguish them, because picking "the biggest" would hand jemalloc's user the unit tests. The filtered database is written to `<project>/.cache/coon/flavours/<hash of the key>/`, inside the project beside `.cache/clangd` rather than in a temp dir, because clangd keys its background-index shards by the database's directory: a temp dir would mean a cold index on every launch, while a stable per-flavour directory keeps each build's shards apart and finds them again next time. It is a cache and can be deleted at any time; the first run of a flavour indexes from cold, which `INDEX_WAIT_TIMEOUT` and the re-query on a later `end` already cover. **And a call graph is of one project.** One flavour left one thing still moving: a callee clangd names in an `outgoingCalls` reply was tested against nothing, so libc and the system headers entered the graph as leaves, and which declaration a `strchr` resolves to depends on the same live header view — three dumps of the same flavour agreed except for four `ctl_lookup -> strchr` edges into `/usr/include/string.h`. Both doors into the graph now ask the same question, and it is the project **root**, canonicalised (`lsp::service::project`): the discovery filter used to test membership of the *compilation database*, which lists translation units, so jemalloc's functions defined in `include/jemalloc/internal/*.h` — real project code, and the bulk of what it inlines — were never discovered at all (1,766 seeds where the root rule finds 2,751). A dropped item never becomes a node, so it is never learned as a `CallHierarchyItem` for a prepare that need not be sent, never enqueued in the warmup and never counted in a `+N`. On jemalloc with `--flavour src/jemalloc.c`: 2,756 functions and 10,545 edges, three runs byte-identical, where the same flavour was 2,340 functions and 10,556–10,560 edges before — 1,858 edges into system headers gone, 1,837 edges from the newly seeded header inlines in.
- **Open documents are a cache, not the project.** clangd's memory is dominated by what it has *open*, not by the project's size: each open document costs a live AST worker and a resident preamble index. The preload exists only to make clangd load `compile_commands.json` and start indexing, and one `didOpen` does that, so the loader opens one file and leaves it open; `LspService` keeps at most `OPEN_DOCUMENT_LIMIT` documents open (LRU, `service::document`) for everything the user asks for afterwards. Closing is a memory measure and nothing else: a document's preamble publishes its view of every header it includes into clangd's merged index, and `didClose` does **not** retract it — a view was measured still standing eight seconds after the close — so `close_all_documents` cannot change what a query answers. Everything after that is served either from clangd's index (`workspace/symbol`, and the `outgoingCalls`/`incomingCalls` that follow a prepare) or from a document `ensure_document_opened` reopens on demand. A document with a request still outstanding against it — a prepare, a find-references, a document-symbol query — is **pinned** and never the one evicted: closing it would answer that request with "trying to get AST for non-added document", silently, since the symbol merely comes out with no edges. The worker records which document each request reads (`LspWorkerState::request_documents`) and the LRU closes the oldest *idle* one instead; if everything over the limit is pinned the set runs over it until the replies land. This used to be an arithmetic promise made from `core`'s side — a 4:1 ratio between `OPEN_DOCUMENT_LIMIT` and the warmup's concurrency — which held for the request rate the warmup was designed at and for nothing else. What the `const` assertion beside `WARMUP_IN_FLIGHT` enforces now is the overshoot: the warmup's prepares in flight plus the files it opens ahead must stay under half the limit, so the other half is there for the user's own requests and the limit stays a ceiling on memory. On jemalloc (217 TUs) the limit is the difference between ~3.2 GB and ~1.7 GB; what is left is the background indexer, which no amount of closing touches.
- **The discovery query waits for the index.** `workspace/symbol` is answered from clangd's background index exactly as it stands the instant the request arrives — clangd never blocks on the indexer — so a query sent early describes a *sample* of the project. It is capped as well: `--limit-results` defaults to 100, and clangd applies that before `handle_workspace_symbols_response` filters the reply down to functions in project files, so on jemalloc the same 100 results came back as anywhere between 15 and 57 functions, and since those are the only seeds the warmup ever expands, the graph came out a different size on every run (481 to 585 nodes over the same unchanged tree). Both halves have to be fixed: clangd is spawned with `--limit-results=0`, and `loader::await_background_index` holds the query until the indexer reports itself done — which took ~2,700 functions and ~3,300 nodes where it used to take 15. That report exists only because `initialize` sets `window.workDoneProgress`; without it clangd marks its background-index progress `Unsupported` and sends no `$/progress` at all, which is what the two `sleep(500ms)`s in the loader were standing in for. Three things about the wait are not optional: `window/workDoneProgress/create` must be answered or clangd reports nothing; an `end` is believed only after `INDEX_SETTLE` of quiet, because the indexer's queue drains between batches and an early `end` is a lull, not the finish; and every wait in the loader has to notice an `end` itself, because they all drain the one response channel and a progress message read by one is gone from the next. When `INDEX_WAIT_TIMEOUT` expires first the query goes out against a partial index anyway — a partial graph beats a blank one while nothing is interactive — and `run_tui_lsp_bridge` repeats it once indexing finishes, which lands as an append because `CoreApp` ingests workspace symbols whether or not it issued the request. **And it waits for the open documents, too.** The reply is the static index *merged with a dynamic index of whatever has been open*: building a document's preamble publishes that document's view of every header it includes, last writer per header wins, and a close does not unpublish it — so the answer is decided by which files the process has ever opened and in what order their preambles landed. Opening all 217 was a lottery between them, most cancelled by the LRU before they published, and jemalloc's headers have two views (its 149 test TUs compile with the `jet_*` defines, its 68 library TUs with `je_*`): one clangd answered 4,041 project functions with a library file open against 4,594 with a test file open, which is where the run-to-run size came from — not from shard loading, which an earlier diagnosis blamed. So the loader opens **one** file, the first in sorted path order so it is the same one every run, and syncs on its `textDocument/documentSymbol` before querying — that reply means the AST, and so the preamble under it, is built. Two processes given the same open history answer identically, symbol for symbol.

- **Edge warmup**: workspace symbols carry no edges, so a freshly loaded project is a heap of isolated nodes — and `logic::cluster` drops isolated symbols, so the clustering comes out empty and the cluster map the app opens on has nothing to draw. Once the load reports `Completed`, `CoreApp::pump_edge_warmup` walks the loaded symbols through the same prepare/follow-up path a manual expand uses. The queue is fed, not seeded: `Completed` is not the instant symbols stop arriving — the loader's discovery reply can land after it times out, and Ctrl+R fetches more whenever the user asks — so every symbol from a *query* enqueues itself through `CoreApp::ingest_symbol`. It is not cascaded into the callees a reply discovers: following those would walk the whole program, which is why a loaded project holds far more functions than the warmup ever claims. While it runs, `CoreApp::loading` still reports the graph as arriving — `Completed` says the *symbols* have stopped coming, not the edges, and clustering a heap of isolated nodes produces nothing to draw. It also reports itself as `AppEvent::ResolvingCalls { done, total }`, because `LspProgress(Completed)` is not the end of the wait and a frontend that showed only the phase announced "ready" over a graph still growing edges. "Running" means the warmup's *own* requests are outstanding, not anyone's: counting every pending request let a single click after the drain restart the state, re-announce the finish and recluster the whole program over a graph one edge bigger.
- **The warmup spends prepares, not follow-ups.** A symbol's edges are one `callHierarchy/outgoingCalls`, which clangd answers from its index in a few milliseconds and needs nothing for but the `CallHierarchyItem` naming the symbol. Getting the item is the cost: `prepareCallHierarchy` runs against the file's AST, so it opens the file (a preamble build, ~250 ms on jemalloc) and parses it. Measured on jemalloc's 2916 symbols, the prepares were 574 of the 623 s clangd spent, and the wall time was that divided by the eight in flight: 79 s. Three things cut it to ~8 s, with the same graph out the other end (per-symbol callee sets differ between two runs of the *old* code in ~365 of 2250 symbols, from where clangd's index places a `jet_*` declaration that run; the new code differs from the old by the same amount, and by the same amount whichever route a symbol took). First, **an item from any reply is the prepare's answer.** Every calls reply carries an item for each callee it names, minted by the same code from the same index as a prepare would mint, and the protocol preserves `data` on any item the server produced for exactly this — it is how an editor's call-hierarchy tree expands a level without preparing every node. `LspBridge::hierarchy_items` keeps every one, `process_call_entry` learns them as they land, and `send_call_hierarchy` — the warmup's and a click's alike — goes straight to the follow-up for a symbol it holds one for. Under hash order 2125 of the 2897 prepares were for symbols an earlier reply had already named. Second, **the remaining prepares are grouped by file** (`core::warmup::WarmupQueue`): `WARMUP_LANES` files at a time, each opened once for all its symbols where hash order changed file on 95% of consecutive prepares and reopened each of the project's files nine times; the next `WARMUP_PREFETCH` files are opened *ahead*, so clangd builds their preambles on another thread while the current ones are read (240 ms for a first prepare that opens its own file, 15 ms once the open led it by 300 ms). Three lanes because clangd retains three idle ASTs and rebuilds any other on every request — at eight lanes the prepare median is 29 ms, at three it is 3–6 ms, and eight measures a quarter slower for fewer prepares. A lane takes the file with the most prepares left and works it bottom-up: C defines before it uses, so the callers are at the bottom, and a prepare there seeds a cascade of follow-ups that covers what is above it before the lane gets there (a third fewer prepares than top-down, replayed against two runs' logged replies). Third, **two budgets**: `WARMUP_IN_FLIGHT` prepares, since each occupies an AST worker and a document; `WARMUP_INDEX_IN_FLIGHT` follow-ups on top, since each occupies neither. The ready follow-ups are sent first, and while they are backed up behind a full pipe the lanes hold, because that is the moment a prepare is most likely to be for something the next reply hands over. What is left is about 1500 prepares from ~115 files at 3–6 ms median, and the run-to-run spread is clangd's: the discovery reply itself varies by a few hundred raw symbols between runs. A side effect worth knowing: ~44 seeds whose prepare returned no item at all — macro-defined functions clangd cannot prepare at their definition — are now resolved through an item some reply carried, so they have edges they could never have had before.
- **A background fetch is not a redraw.** Every request carries a `RequestOrigin`, and only `User` answers emit `AppEvent::LayoutDirty` — which is what every out-of-process frontend turns into a full snapshot. The warmup used to answer with one per reply: on jemalloc that was 767 whole-graph snapshots in 110 seconds of loading, of which exactly one changed the screen, because the map the app opens on has no root and draws no call edges at all. The client answers a snapshot by tearing the canvas down and re-rendering a sidebar holding every symbol in the project, so this was the lag. Nothing is lost by the silence: the graph still grows, and the map is not computed until it stops. The origin has to survive the prepare → follow-up hop, since the second half is the one that carries the edges. `EventRouter` holds a second line of defence, rate-limiting snapshots to `LOADING_SNAPSHOT_INTERVAL` while `ResolvingCalls` says the warmup is running — holding one back, never dropping it, and releasing it the moment the warmup drains.
- **The snapshot ships what the client reads, and borrows it.** `core::protocol::WireGraph` is not `CallGraph`: the client never touches a node's `references` or `diagnostics`, nor an edge's `call_location`, and those cost more than everything it does read put together — 4.63 MB of a 5.97 MB jemalloc snapshot was call sites dropped on the floor. Edges go out one per caller/callee pair rather than one per call site, because that is what the client was already reducing them to on arrival. Same graph, 2.05 MB instead of 5.97 MB. It borrows the app rather than owning a copy, which is why `snapshot_of` returns a `ServerMsg<'_>` and both backends serialise it while still holding the lock instead of handing the message around. Field names match what `app.js` already reads; shortening them would save a little more and cost the client a rewrite.
- **Loading is reported in the status bar, and only there.** It has two stages — clangd handing over symbols (`LspProgress`), then their edges (`ResolvingCalls`) — which the client folds into one `load` object in `app.js`. That object exists to keep the one status line honest: the transient events used to fight over it, and a warmup reply would set it to "Ready" while the project was still indexing. A stage carrying a total reads as a fraction, one without as a running count, since clangd streams workspace symbols without ever saying how many are coming. The TUI shows the same two stages in its own status bar, reading `CoreApp::warmup_progress()` directly.
- **The cluster map is modularity, on a resolution ladder.** `logic::cluster` optimises modularity with the Louvain method: sweep the functions in symbol-id order, move each into the neighbouring box that gains the most, repeat until nothing moves, collapse every box into one node, go again. Each collapse is a rung, so the levels are a **zoom** — every level partitions the same functions, and the client shows exactly one at a time (`Command::SetMapLevel`, per workspace) rather than opening boxes. It replaced heavy-edge matching, which grouped by what merges cheaply: 328 of a real project's 370 calls weighed one, so "heaviest" was a tie decided by symbol id, and `log_write`, `mem_free` and `strcmp` grew a box of every caller they had — 26 of the 33 boxes the map opened on spanned more than one file. Under the null model a call to something everything calls is expected and does not pay for a merge, and a sweep can undo a grouping a previous sweep made, where a pair once matched was matched for good. The rungs are resolutions: one pass per entry of `RESOLUTION_LADDER` (8, 4, 2, 1) *as multiples of the chosen γ*, finest first, then passes at γ until the optimiser is done, then — only while the top is wider than the chosen target width — halvings below it. A pass that merges nothing adds no rung. **The quotient of every rung is a DAG.** Modularity alone puts no constraint on direction — a box can sit on both ends of a one-way path — and on a real project 19 of the top rung's 55 lines ran both ways over a call graph with no cycle in it. So a move is refused when the box it joins would land on a directed cycle of the quotient (`joins_a_cycle`), the next-best candidate is scored instead, and the singleton fold is held to the same rule. The base graph is condensed by strongly connected component first, so mutually recursive functions are one unit from the finest rung up. On that project it cost 0.04 of modularity and four boxes at the opening rung; the check is a BFS over the quotient per candidate move, which is the cost to watch on a large project.
- **Where the ladder stops and where the map opens are different questions.** `Ladder::opening` — carried through as `Clustering::opening_level` and the default in `CoreApp::map_level_for` — is the last rung built at plain modularity, the grouping the objective stands behind. Rungs past it exist only when that one was wider than the target: they merge modules that did not want to merge, to fit a count, and are where a user zooms out *to*. `cargo run -p core --example rungs` prints the ladder with density and mutual-pair counts (which must read zero), and given a cluster-map DOT export it rebuilds that project's graph and prints its — which is how the method was judged without a clangd run. What that judging found, and is still open: from calls alone no objective recovers the source tree on a layered C project. The by-file grouping of the 188-function example has modularity 0.32 where Louvain finds 0.58, because a module there is a layer whose functions share callers and callees rather than a dense clique — so the fine rungs track files well and the top rung groups by lifecycle phase (everything `_init`, everything `_free`). Neighbourhood-similarity weighting, directed modularity and stripping leaves were all measured and none closed the gap; the lever left is the file path, which the graph carries and the clusterer has so far deliberately not been shown.
- **The map is drawn where the functions are.** A box is placed by its members, not by a layout of its own: `core::layout::compute_map_frame` lays every function in the graph out at once and keeps where each one landed, and each rung then puts a box at the average of its members' seats. Laying the quotient out from scratch — which is what this replaced — made every rung a different picture of the same program: the boxes a zoom step merged landed wherever crossing minimisation put them, so zooming shuffled the canvas instead of coarsening it, and the box holding `main` had no reason to sit anywhere near where `main` sits in the call tree. Four things give way in order, and the order is the point: a box's layer is held to what the calls allow, so the map is as many columns as its longest chain and a layer nothing lands on is closed up rather than drawn; the frame's cross axis is rescaled to a pitch, one scale for the whole map so that a box and the box it calls still line up; boxes that end up on top of each other are pushed apart by the least that clears a node, in the frame's order, with the column slid back so its middle has not moved; and every box is snapped to a whole row. Order is defended to the last, absolute position gives way. The frame is per *graph*, not per rung or per target, so it is computed on the worker thread that computes a clustering (`Clustered`, in `app.rs`) and every map is placed from the one copy — at a few hundred milliseconds over a real project it is far too slow to do per snapshot, and nothing about it changes between rungs. A box none of whose members has a seat — the frame is one generation behind a graph that just grew — waits in a lane past the last column. Because the map now holds still, the client does not refit on a zoom step: the rung is not part of its fit key.
- **A mean is where a box belongs; it is not a layering.** `MapFrame::seat_of` averages a box's members' layers, and an average pays no attention to the quotient's order — box A can call box B while A's members average deeper than B's. So the map did not read in the direction it named: measured edge by edge along the reading axis, 3–22% of the arrows on a left-to-right map pointed backwards, and another 5–17% joined two boxes in the same column and so made no progress at all, worst at the coarse rungs where the map is meant to be most readable (Leiden's rung 4 of the 279-function export: 11 of 49 edges backwards). That is repairable rather than fundamental, because the quotient of every rung is a DAG — see above — so a legal layering always exists. `level_boxes` holds each box to the layers the quotient allows: the map is as many layers as its longest chain of calls, which is the fewest any forward-reading drawing can have; each box has a window inside that, `early` being the longest chain of callers behind it and `late` that count less the longest chain ahead; and the mean is the preference, clamped into the window and then lifted where a clamp of a *rounded* mean still leaves an edge flat. The levelling is done once in the frame's own direction, so an incoming map is the outgoing one in a mirror rather than a different picture levelled the other way. **Minimum layers is not a nicety — it is what keeps the map two-dimensional.** The first attempt used the mean as a hard floor instead, `max(preference, caller + 1)`, which removes every backward edge and is wrong in a way worth recording: a rule that can only push boxes apart never compacts, so it spent twelve columns on a ten-layer rung and flattened the export's *opening* map to 2442×0 — a line, on which the whole cross axis the bullets above are about does not exist. The clamp is also deterministic, which a minimum-displacement optimiser is not: "lift the callee or pull the caller" is a genuine tie, and resolving it differently on adjacent rungs is exactly the shuffle the frame exists to prevent. Measured over both graphs, all three methods, every rung, both orientations and both directions — 84 combinations — every map uses exactly longest-chain-plus-one columns and not one edge runs backwards or stays in its column. The only single-row map left is one whose quotient really is a chain (Markov's coarsest rung: five boxes, four calls end to end). A side effect worth knowing: the columns it stops spending are also what made the map a ribbon, so the export's finest rung went from 6810×503 to 5106×1514 over this and the pitch below — a quarter narrower and three times taller, on the same graph.
- **That scale is a pitch, and the box count is only its floor.** It used to be the count itself: the whole map's cross extent mapped onto `crowd - 1` slots, which is the span the busiest column needs stacked back to back at the minimum separation. That is scale-to-the-floor rather than scale-to-fit — for any graph, of any shape, at any rung, that column came out at the minimum by construction — and it was worse than the floor, because the numerator was the busiest column's box *count* while the denominator was the global extent of every box on the map. The busiest column only ever occupies a fraction of that span, so its boxes landed closer than one slot and the push placed them, which threw the frame's distances away before the step meant to defend them ever saw them; and one outlying box in a sparse column squeezed the whole map tighter still. It measured as a single number: every gap between adjacent boxes, on every rung, of every method, on the demo and on a 279-function export, was exactly 26px, with 70–100% of adjacent pairs sitting at the floor. The scale is now chosen so the busiest column averages `MAP_CROSS_SPREAD` (2) map pitches between neighbours over the span *its own* boxes occupy — two rather than one because one is the floor as an average, and half of any real column would still be pushed. Where several columns tie for busiest, which on a real project's finer rungs is most of them, the target is averaged over all their gaps together: letting the widest of them set it leaves every tighter one to the push and puts the rung's median back at the floor, and letting the tightest set it flings the rest out to the cap. **The cap is measured against the map's content, not its level extent.** `MAP_CROSS_CAP` (3) times what the busiest column asks for is what keeps a tight busiest column from flinging a far-off box off the canvas — the same point `MAX_LEVEL_STRETCH` makes on the other axis. Taking it from the level extent instead is the obvious thing and is wrong: a scoped map two or three columns wide has a level extent that says nothing about how much room its boxes need, so the cap would squeeze exactly that map back to the floor, which is this whole bug again for narrow maps. As content it binds on one rung of one method in everything measured, by under one per cent — a guard, not a shape the map is pulled towards. On the export's opening rung the map goes from 6810×503 to 6810×1575, its median gap from 26px to 140px, and its share of pairs at the floor from 70% to 22%, with the order of the boxes in every column unchanged — which is the property the frame exists for, and the one to check first if this is ever touched again.
- **The map sits on rows, because the tree does.** The rooted tree's nodes are on a lattice by construction — `grid` hands out integer slots and the pitch is applied after — so any two of them are either exactly level or a clean multiple of the pitch apart, and that is what makes it read as a grid rather than a drawing. Nothing in `place_boxes` put the map on one: the scale gives each box an arbitrary real, the push makes a *gap* whole without making a *position* whole, and the recentring then subtracts a fractional drift from every box in a crowded column, which on its own guarantees nothing in it lands on a row. Measured against the tree, which is at 0.000 off-lattice with no near-misses, the median box sat about a fifth of a pitch (~17px) off any row, one box in twenty-nine was on one, and boxes in neighbouring columns landed 5px apart — visibly not level, far too close to read as different rows. That is what a user comparing the two screenshots sees as the map looking slumped and hand-placed, and it is invisible in every aggregate the two fixes above are measured by, which is worth remembering: a picture is the test for a layout. Each slot is now rounded to the nearest whole one. Whole and not half, because a half-slot in the tree is a parent centred over two children and means something, where on the map it would be the frame's noise at twice the density. Rounding cannot collide two boxes: `round` is monotone and `round(x + 1) == round(x) + 1`, so two slots the push left a slot or more apart round to slots a slot or more apart, and the order survives with them — the walk still holds each box past the one before, as a statement of the invariant rather than a repair, and over 84 maps it never once had to act. The column is deliberately not recentred afterwards: a fractional recentring goes straight back off the lattice, and a whole one moves every box a full pitch to correct a displacement that is a fraction of one. **What it costs is that the gaps move by up to half a slot each way** — one slot and a bit under a half becomes the floor, a slot and a half becomes the two-slot target — so the share of gaps sitting exactly at the floor rises from about a quarter to about two fifths. The map is not more crowded for it: the cross extent comes out within a few per cent of where it was on every rung measured. Gaps that were near the floor now land on it, which is what a lattice means.
- **The map's gutters are its own.** `MAP_ROW_GUTTER` (48) and `MAP_SIBLING_GUTTER_TOPDOWN` (64) rather than the tree's `ROW_GUTTER` (26) and `SIBLING_GUTTER_TOPDOWN` (40), because adjacency in a column means something different in each. In the rooted tree two nodes stacked in a column are siblings — one caller reached both — so a tight gutter reads as kinship, and it is right that it does. On the map two boxes stacked in a column are unrelated modules that happened to average into the same layer, and the tree's spacing asserts a relationship that is not there. The map had the tree's pitch only because it borrowed the tree's geometry along with its frame, which is the kind of sharing that is invisible until someone asks why the picture feels crowded.
- **The last rung folds its leftovers.** A function no box gains by taking in comes through as a box holding one function beside boxes holding thirty; on a real project that was `fputc`, alone, next to clusters of 22 and 29. `fold_singletons` merges each of those into the neighbour it shares the heaviest edge with, and is composed into the last round rather than added as a rung, because it is a repair to the top of the ladder and not a step of the zoom. It is the one place the objective is overruled.

- **A clustering is computed once, when the graph stops moving.** Coarsening is not incremental: a run over a graph that gained a thousand functions is a different ladder, not the same one extended. So `CoreApp::sync_clusterings` starts nothing while `loading()` is true — an LSP phase short of `Completed`, or an edge warmup still running — and after that computes what is owed, one job at a time on a worker thread. Demo mode is the exception and is clustered in `with_bridge`, because a graph that arrives already populated is the whole of it and no loader will ever say so. The cache is one table keyed by `ClusterTarget` (the settings, and the scope — which is a function, a direction and a depth together) rather than a whole-program clustering plus a table of scoped ones, which is what makes one staleness rule and one job queue cover both; a target's staleness is cleared at *spawn*, so a batch landing mid-run is owed again rather than swallowed. The whole-program map for each method in use is never evicted, because it is what a new tab opens on and what widening a scope goes back to.
- **A scoped map reaches exactly as far as the view it was scoped from.** `Command::SetMapScope` draws the map of one function's neighbourhood, and that neighbourhood is walked to the workspace's own **depth** (`cluster_within`, via `logic::GraphTraversal::find_reachable_within`): a map of "what `f` reaches" that reached further than the tree the user asked for it from would draw boxes holding functions they cannot see. The depth is the only part of the on-screen window the map takes. `collapsed` and `expanded` are not, because they describe one tree's shape rather than how much program is in view — and a map that regrouped and renamed its boxes on every collapse click would be describing the clicking. The **whole-program** map takes no depth at all: it starts nowhere in particular, so there is no walk for a number of levels to bound, which is why the depth lives inside `ClusterTarget`'s `scope` and not beside it — a depth on the unscoped key would split the one cache entry every tab falls back to and rebuild it on every press of a stepper that does not govern it. In the client `depthApplies()` says the same thing once: the depth pill is live on the call tree and on a scoped map, inert on the whole-program map, where the zoom control beside it is what moves instead. Its bracket hints are dropped on any map, because there those keys are the zoom.
- **The method is a value, not a constant.** `logic::ClusterMethod` has three variants, `Modularity`, `Leiden` and `Markov`: every method makes a different claim about a program's shape, and which claim is on screen is the user's to pick. It travels on the workspace beside depth and orientation, in `Command::SetClusterMethod`, and in the snapshot's `cluster_methods` — which the client renders into its picker rather than carrying its own copy of the list, so a method added in `logic` is reachable without touching the client. Adding one means a `coarsen` arm and a `Coarsening::by_…` phase plan; the base graph, the ladder shape, the singleton fold, the flattening and the labels are shared.
- **And so are the knobs it reads.** `logic::ClusterSettings` is the method *and* its parameters as one value: γ for the two modularity methods (`RESOLUTION_LADDER` is multiples of it, so moving it moves every rung rather than only the opening one), the inflation for Markov, and the width the ladder coarsens towards, shared. One value rather than a method beside a bag of parameters, because they are one question — a workspace holds one, a worker computes one, and `ClusterTarget` is keyed by the whole of it, since the same method at another grain is a different ladder and serving one for the other draws a map the user's knobs do not describe. Every method's knob is carried, not just the selected one's, so tuning the flow and coming back to modularity has not moved γ. It is stored in hundredths, because a cache key made of floats is one that two equal-looking requests miss each other on; `WireSettings` is the hop to the plain numbers the wire and the API speak, and it *sanitises* — clamped to the range and snapped to the step — so nothing out of range can reach the ladder from a frontend at all, and `CoreApp` has nothing left to validate. What a control needs to draw one travels with it as a `SettingSpec` (range, step, default, label, and one line on which way to turn it), per method in `cluster_methods[].grain` and once for the shared one in `cluster_top`: a method added in `logic` with a knob of its own arrives in the panel already drawn. `TARGET_TOP_CLUSTERS`, `MARKOV_INFLATION` and `DEFAULT_RESOLUTION` are now the defaults these start at rather than the values the ladder is built to.
- **Leiden is the third method, and the second climb of the same objective.** `ClusterMethod::Leiden` optimises modularity with the Leiden algorithm (Traag, Waltman and van Eck, 2019) in place of Louvain, and its ladder is modularity's pass for pass — `Coarsening::by_modularity` takes the pass as a parameter. What it adds is a guarantee: every box is connected by the calls among its own members. Louvain cannot promise that — a node that was the bridge between two halves of its box moves out, and the halves stay together because a collapsed box is never re-examined — so Leiden puts a *refinement* between the moving and the collapsing (`refine`): every box is broken back into singletons and rebuilt by merging only nodes well connected to the box into sub-boxes well connected to it, and the graph is collapsed by the refined partition while the unrefined one is handed on as the next round's start. One run to convergence is one pass (`leiden_pass`); the rounds inside it are scaffolding, not rungs, because the unrefined partitions do not nest across rounds. Two departures from the paper, both deliberate: the merge is the best-gaining one rather than a random draw weighted by gain (the zero-temperature limit, so the module stays deterministic; it forfeits only the guarantees that need unbounded iterations), and every refinement merge is held to the DAG rule too, since a finer partition of an acyclic quotient need not be acyclic — a chain of three in one box is a two-way cycle once its ends are split from its middle. A cycle of the refined quotient never leaves a box, so that check is confined to the box under refinement. The moving phase is the paper's queue rather than a full sweep (`Mover::drain_queue`); Louvain keeps its sweep (`Mover::sweep`) and is byte-for-byte what it was. Measured with the `rungs` example, which now prints a `split` column (boxes that are not connected) and `Q`: on the demo and the 62-function tree export Leiden's opening rung is Louvain's, box for box; on the 188-function example it opens on 16 boxes to Louvain's 13 at the same purity and a higher modularity (Q 0.528 to 0.516), and its Q is at or above Louvain's on every rung of all three. Louvain produced no split box on any of the three — the guarantee is a promise at this scale, not a repair — while Markov produces one or two on each, because its drain step follows two-step flow and can put a node in a system it shares no call with.
- **Markov flow is the second method.** `ClusterMethod::Markov` runs van Dongen's MCL over the symmetrised call matrix — expand (square), inflate (raise every column to the chosen inflation, `MARKOV_INFLATION` = 2 by default, and renormalise), prune, until the flow settles — computed sparsely per column, since dense squaring is cubic in the function count. One pass over the base graph is the opening rung: MCL is not an optimiser climbing to an optimum, a run *is* the answer. Coarser rungs re-run it on the quotient, easing the inflation towards one only while the top is wider than the target; there are no finer rungs, because MCL partitions at different inflations do not nest and a ladder is a chain of refinements. The DAG rule is enforced where the settled flow is read off into boxes (`markov_pass`): attractors that feed each other are united only if the quotient stays acyclic, and every other node drains into the best legal system — by flow, then by direct calls, since settled flow is all-or-nothing and offers no second candidate — swept to a fixed point, because whether a join closes a cycle depends on which of its neighbours are already in. Measured with the `rungs` example: on the demo it opens on 4 boxes with one holding 34 of 57 functions (directory purity 0.49 to modularity's 0.6+), and on a 62-function tree export on 7 boxes at 0.48 to modularity's 0.58. The hub blob is textbook MCL at inflation 2 — it is there with the rule switched off too — and the inflation is the one lever: 2.3–2.5 splits the demo into 14–17 boxes, and the count is not monotone in the self-loop weight, so neither was tuned on two tiny graphs. That lever is now the user's, on the settings panel, which is the honest place for a number nothing here could tune for every project.
- **The hint line yields; a result holds it.** `#info` has many writers — hovering a node writes the symbol under the pointer, leaving it writes an empty string, a regrouping writes that the map moved — and during the warmup that is constant. Right for a hint, wrong for a result: an export names the file it just wrote, and on jemalloc that line was gone before it could be read, overwritten by the next `ClusteringUpdated` or by the mouse crossing the canvas, which made a working export look like a key that did nothing. So `setInfo` is a hint and yields to anything held, `holdInfo` is a result and outranks them for `INFO_HOLD_MS`. Same reason the `load` object exists for the status bar: one line, several writers, and only one of them saying something worth waiting for.
- **An export is a view, in Graphviz DOT.** `core::export` renders what is on screen — this workspace's depth limit, collapsed and expanded nodes, direction and orientation already applied — and nothing else; exporting the whole loaded graph would hand back ~3,300 nodes nobody has ever looked at, which is what the mechanisms in `layout` exist to prevent. DOT rather than SVG or PNG because it is already the interchange format of C/C++ call graphs (doxygen, egypt, gprof2dot, callgrind all emit it), `dot -T…` turns it into every raster and vector format afterwards, `networkx` and `gvpr` read it *back* as a graph, and — the reason that decided it — `subgraph cluster_…` is a native DOT concept that the cluster map maps onto with no translation at all. A map export draws what the canvas draws: calls inside a box one per function pair, since opening the box is what the file is for, and calls between two boxes as **one line per pair of boxes**, border to border (`compound=true`, `ltail`/`lhead`), anchored on the heaviest function pair across it and carrying the summed count in its tooltip — thirty lines fanning between the same two boxes was a drawing of something the screen never showed. The trade is that the file no longer records which functions call across a border, only the pair of boxes and the total; `rungs` rebuilds a graph from such an export with that granularity. Being text is what lets one implementation serve all three frontends: the TUI cannot render a PNG and the web client would need a rendering library to. It carries no colour, because the canvas reads its palette from the CSS custom properties and a second copy in Rust would drift. `CoreApp` builds the bytes and stops there — `AppEvent::GraphExported` hands them to the frontend, because where a file belongs is the one part of this that differs per pipe, and a web server writing to its own disk on behalf of a tab on another machine is the wrong answer in the only case with a network in it. TUI: `e`, into the working directory. Web: `Ctrl+E`, a download — the only place a page can put a file. Desktop: `Ctrl+E`, and `save_export` **asks**, opening a native save dialog on the project directory; choosing for the user sent three exports to whatever XDG calls downloads, which on a `XDG_DOWNLOAD_DIR="$HOME/"` machine is the home directory. The dialog is opened from Rust, not from `transport.js`: a plugin's JS bindings come as an npm package and reaching for one would cost this client the property that it is a plain script with no build step. `CoonHost.saveFile` resolves to the path, or to `null` for a cancelled dialog — not a failure, and not reported as one. Both halves live in `transport.js`, with the window controls, for the same reason they do.
- **`grid` crate**: provides the tree layout algorithm used by `GraphView` and by `core::layout::compute_layout`.
- **One protocol, many pipes**: `core::protocol` is the single definition of what a frontend sees. Adding a fourth frontend should mean writing a transport, not a protocol.

### Gotcha: the crate named `core`

The workspace crate `core` shadows Rust's built-in `core`. Crates that use macros expanding to `::core::…` paths (Tauri does) must alias it:

```toml
coon_core = { package = "core", path = "../core" }
```

`crates/desktop` does this. Others refer to it as `::core::`.
